Architecture

What we're building.

An in-line sidecar gateway that enforces deterministic effect checks against the system of record before tool execution.

Current agent security tools rely on intent detection: asking a secondary LLM whether a prompt appears malicious. In an autonomous business agent equipped with real tool credentials, this approach inevitably fails because natural language prompts cannot be reliably partitioned by syntax alone.

LEASH replaces probabilistic prompt filtering with a deterministic action gateway. Sitting as an inline sidecar between the LLM and backend execution tools, LEASH does not attempt to guess what the model "intended." Instead, it intercepts the structured action contract and validates it against system of record ground truth.

FIGURE 1: THE ENFORCEMENT BOUNDARY Sidecar Topology

LEASH intercepts agent dispatches, validates invariants against SQLite records, and mints an HMAC receipt required by tools.

1. Recipient Identity

The refund recipient email must strictly match the original payer recorded in SQLite. Diverting to an attacker's wallet is impossible.

2. Balance Preservation

The requested refund cannot exceed the order's remaining refundable balance. Overdraw attacks fail deterministically at Stage 3.

3. Quorum Enforcement

Transactions exceeding $300 require a second signature from a human supervisor before an HMAC token can be minted.

The Threat Model

Why this approach.

Prompt intent is probabilistic and porous. State mutations are concrete and provable.

In a tool-augmented agent architecture, an attacker can format indirect prompt injections in low-resource languages (Kannada, Hindi), embed them in customer support tickets, or encode them in Markdown. An NLP guardrail must predict every possible linguistic evasion across all languages.

A state invariant only checks one equation. Whether an injection was written in English, Kannada, or Base64, the proposed tool dispatch still asks to send money to a destination. LEASH checks the destination against the verified customer database.

def verify_gateway_receipt(action_payload: dict, receipt_token: str) -> bool:
    expected_token = hmac.new(
        GATEWAY_SECRET, canonical_json(action_payload).encode(), hashlib.sha256
    ).hexdigest()
    if not hmac.compare_digest(expected_token, receipt_token):
        raise SecurityException("UNAUTHORIZED_ACTION: Missing or invalid LEASH receipt")
    return True
Transparency

Known limitations, stated honestly.

Operational boundaries: what LEASH protects and what it does not attempt to solve.

Pre-Tool Token DoS

LEASH intercepts actions at the tool boundary. If an adversarial prompt forces the LLM into an infinite conversational loop, LEASH cannot stop the token spend.

Quorum Fatigue

If an attacker continuously proposes transactions requiring supervisor approval, human operators may face review fatigue. Circuit breakers mitigate this.

Schema Synchronization

System-of-Record invariants require schema synchronization with core business databases. Schema drift without policy updates can cause false blocks.

1. Exploit escape rate and false block rates were measured on LaunderBench-mini (n=90) under controlled adversarial test conditions.
