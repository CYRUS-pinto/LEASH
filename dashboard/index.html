2. Architecture • Dual-Token Airgap

What we're building

Autonomous enterprise agents are being granted direct API access to corporate databases, email inboxes, customer records, and payment processors. When an autonomous agent processes an untrusted email or ticket, an attacker can embed an indirect prompt injection.

Because LLMs process data and instructions in the exact same token stream, the agent inevitably treats the attacker's text as a command. Existing defenses attempt to guess the agent's internal intent through prompt classifiers or text guardrails. But an LLM is a probabilistic engine: given novel paraphrasing, encoding, or foreign language translations, text guardrails fail.

The LEASH Airgap Boundary

LEASH places an air-gapped deterministic gateway between the untrusted agent and corporate tools. The agent never holds database credentials or payment API keys. When the agent wants to act, it proposes the action to LEASH (:8000). LEASH verifies the concrete effect against the authoritative database and issues a signed HMAC receipt. The protected tool server (:8001) strictly refuses to execute any request lacking this cryptographic receipt.

3. Threat Model • OWASP LLM #1

The Control Gap: Autonomy × Access − Enforcement

In traditional systems, user permissions are tied to authenticated human identities. But in agentic architectures:

  • The Agent Obey What It Reads: One poisoned invoice or webpage turns your own customer service agent into an insider threat.
  • Logs Are a Rear-View Mirror: Current security tools log what agents say after the incident occurs. Nothing enforces what agents do before money moves or data leaves.
  • The Invariant Rule: An agent's intent is inherently unobservable; an action's effect on the system of record is deterministic and measurable.

5. Pipeline Deep-Dive • 8 Verification Stages

The 8 Deterministic Stages

Every proposed tool invocation passes through eight deterministic gates in under 8 milliseconds:

Stage 0 • Circuit Breaker Quarantines agents after 3 repeated denial violations within a 5-minute rolling window.
Stage 1 • Role-Based Tool Scope Strict allow-list matching: e.g. support agents can never call internal admin endpoints.
Stage 2 • Parameter Constraints Type, range, and format enforcement via Pydantic contract validation.
Stage 3 • System of Record Effect Ground-truth verification against SQLite: refund recipient must match order original payer.
Stage 4 • SQL AST Read-Only Enforcer Parses SQL abstract syntax tree; blocks mutating keywords (DROP, DELETE, UPDATE, ALTER).
Stage 5 • DLP & Secret Redaction Regex scanner for outbound credit card numbers, SSNs, and private API keys.
Stage 6 • Velocity & Budget Caps Enforces 1-hour rolling spend budgets ($3,000) and rate limits (60 actions/min).
Stage 7 • Dual-Control Quorum & Receipt Actions above $300 require supervisor approval; mints single-use HMAC-SHA256 receipt.

7. Engineering Candor • Concessions

Known limitations & trade-offs

To maintain technical credibility with senior security judges, we openly document our system's boundaries and threat model limits in docs/KNOWN_LIMITATIONS.md:

  • Author-Benchmark Confound: We authored both the evaluation benchmark and the defense rules. Zero escapes on 48 traces proves internal architectural consistency, not absolute invulnerability against all possible future injection shapes.
  • SQLite Truncation Resistance: Hash chains detect tampering of existing rows, but complete rollback requires periodic anchoring to an external ledger via leash anchor.
  • Relational Invariant Dependency: SoR effect verification depends on having clear relational schema invariants. Non-relational tools (such as arbitrary third-party webhooks) require custom policy adapters.

Executive Summary

The Problem

Autonomous customer support or finance agents can lose thousands of dollars in seconds from a single indirect prompt injection buried in an invoice or ticket. Logging records the disaster; LEASH prevents it.

The 4 Ground-Truth Pillars

1. Database Effect Matching Refunds must return to the original payer in the authoritative database.

3. Cryptographic HMAC Airgap Tools accept requests only with a signed HMAC receipt from the gateway.
